# 学生管理系统 V2.0 产品需求文档（PRD）

> 文档状态：评审稿  
> 版本：2.0  
> 更新日期：2026-08-09  
> 适用对象：产品、设计、前端、后端、测试、运维  
> 需求依据：现有代码、数据库与本地启动验证结果

## 1. 文档目的

本文档用于将当前可运行的学生信息管理原型升级为可在学校或院系内部稳定使用的学生基础信息管理系统。V2.0 聚焦“数据可信、权限清晰、批量处理安全、操作可追溯”，并为后续学籍、成绩和教务能力预留扩展空间。

## 2. 当前产品基线

### 2.1 已验证技术基线

| 层级 | 当前实现 |
|---|---|
| 前端 | Vue 3、Vite 8、Element Plus、Pinia、Vue Router、Axios |
| 后端 | Python 3.12、FastAPI、SQLAlchemy Async、Pydantic |
| 数据库 | SQLite（`backend/student.db`） |
| 认证 | JWT Bearer Token，默认有效期 24 小时 |
| 导入导出 | openpyxl 生成和解析 Excel |
| 默认账号 | `admin / admin123`，首次启动自动创建 |

### 2.2 已有业务能力

- 用户登录、当前用户查询、管理员创建及查看用户。
- 学生新增、查询、编辑、删除、批量删除。
- 按学号、姓名、手机、班级、性别、状态筛选学生。
- 学生 Excel 导入和导出。
- 班级新增、查询、编辑、删除及学生数量统计。
- `admin`、`editor`、`viewer` 三级角色的后端权限控制。

### 2.3 当前运行验证

- Python 源码编译检查通过。
- 前端生产构建通过；存在 Element Plus 主包大于 500 kB 的构建警告，不影响启动。
- 后端可在 `127.0.0.1:8000` 启动，根接口、管理员登录、学生列表和班级列表均调用成功。
- 前端开发服务可正常启动并返回 HTTP 200。
- 验证时本机 `5173` 端口已被占用，Vite 自动改用 `5174`；使用空闲端口 `5188` 复核成功。
- 仓库未提供根级 README、环境变量模板、自动化测试、迁移脚本目录或一键启动脚本。

## 3. 产品定义

### 3.1 目标用户

1. 系统管理员：维护账号、角色、基础配置与数据安全。
2. 教务/辅导员：日常录入、更新、导入和导出学生与班级信息。
3. 教师/查询人员：按授权范围查询学生和班级信息，不修改数据。
4. 审计/运维人员：定位数据变更、登录异常和批量任务失败原因。

### 3.2 核心问题

- 学生信息分散在 Excel 中，版本不一致、重复录入且难以追责。
- 批量导入缺乏预校验和可下载的错误明细，数据质量不可控。
- 当前前端仍展示用户无权执行的按钮，权限体验与后端规则不一致。
- 删除是物理删除且无审计日志，误操作后无法恢复。
- 默认密码和固定开发密钥使当前版本不适合直接部署到生产环境。

### 3.3 V2.0 能力声明

学校内部授权人员能够在明确的数据范围和角色权限下，安全地维护、批量导入、检索和导出学生及班级基础信息；系统对关键变更保留审计记录，并允许管理员恢复误删除数据。

### 3.4 成功指标

| 指标 | V2.0 目标 |
|---|---|
| 首次部署至可登录时间 | 不超过 15 分钟 |
| 常用查询响应时间 | 95% 请求不超过 1 秒（5 万名学生规模） |
| Excel 导入有效行成功率 | 不低于 99.5% |
| 导入错误可定位率 | 100% 提供行号、字段和原因 |
| 关键写操作审计覆盖率 | 100% |
| 未授权写操作拦截率 | 100% |
| P0/P1 生产缺陷 | 发布时为 0 |

## 4. 范围

### 4.1 V2.0 必须交付（P0）

- 安全登录、首次登录改密、账号启停与密码重置。
- 角色权限前后端一致，页面和按钮按权限显示。
- 学生与班级的完整管理、校验、软删除和恢复。
- Excel 模板下载、预校验、确认导入、结果报告。
- 操作审计日志。
- 仪表盘基础统计。
- 可配置环境、数据库迁移、自动化测试和部署说明。

### 4.2 建议交付（P1）

- 数据权限范围：全校、院系、年级、班级。
- 自定义导出字段和保存常用筛选。
- 批量调班、批量状态变更。
- 通知中心与导入导出任务中心。
- PostgreSQL 生产部署方案与 SQLite 数据迁移工具。

### 4.3 后续规划（P2）

- 院系、专业、课程、成绩、考勤、奖惩和学籍异动流程。
- 学生自助门户、家长端、消息推送。
- 单点登录、组织通讯录同步、第三方教务系统集成。
- BI 分析和风险预警。

### 4.4 明确不在 V2.0 范围

- 排课、选课、考试安排与成绩核算。
- 学费支付、财务结算、宿舍和资产管理。
- 人脸识别、硬件考勤和家校即时通讯。
- 未经审批的 AI 自动决策或学生风险定级。

## 5. 角色与权限

| 能力 | 管理员 admin | 编辑员 editor | 查看员 viewer | 审计员 auditor（新增） |
|---|---:|---:|---:|---:|
| 查看学生/班级 | ✓ | ✓ | ✓ | 只读必要字段 |
| 新增、编辑学生 | ✓ | ✓ | - | - |
| 导入学生 | ✓ | ✓ | - | - |
| 导出学生 | ✓ | ✓ | 按策略授权 | - |
| 删除/恢复学生 | ✓ | - | - | - |
| 维护班级 | ✓ | ✓ | - | - |
| 用户与角色管理 | ✓ | - | - | - |
| 查看审计日志 | ✓ | - | - | ✓ |
| 系统配置 | ✓ | - | - | - |

权限必须由后端最终裁决；前端隐藏或禁用无权操作仅用于改善体验，不能作为安全边界。P1 数据范围启用后，所有列表、详情、导出和统计必须应用同一范围过滤。

## 6. 核心业务流程

### 6.1 首次部署与登录

1. 运维配置数据库地址、JWT 密钥、允许来源和初始管理员信息。
2. 系统执行数据库迁移后启动。
3. 初始管理员首次登录时必须修改临时密码。
4. 登录成功后进入仪表盘；失败时只返回统一错误，不泄露账号是否存在。

### 6.2 单个学生建档

1. 编辑员进入“新增学生”。
2. 系统即时校验必填项、格式、学号唯一性及班级有效性。
3. 保存成功后写入学生记录和审计日志。
4. 返回学生详情或列表，并显示明确的成功反馈。

### 6.3 Excel 批量导入

1. 用户下载带字段说明和示例的当前版本模板。
2. 上传文件后系统只做解析和预校验，不立即落库。
3. 页面展示总行数、新增、更新、跳过、错误及风险汇总。
4. 用户选择“仅新增”或“按学号更新”，确认后执行。
5. 系统生成任务结果及错误文件，支持再次下载。
6. 同一导入任务重复提交不得重复写入数据。

### 6.4 删除与恢复

1. 管理员发起单个或批量删除，界面展示影响数量。
2. 用户二次确认后记录删除人、时间和原因，数据进入回收站。
3. 回收站保留期内可恢复；超过保留期后按策略清理。
4. 永久清理必须是单独权限与单独操作，不得由普通删除隐式触发。

## 7. 功能需求与验收标准

### FR-01 认证与会话（P0）

需求：支持用户名密码登录、退出、获取当前用户、首次改密、管理员重置密码和账号启停。

验收：

- 初始密码不得硬编码在前端页面或生产代码默认值中。
- 生产环境缺少强随机 `SECRET_KEY` 时应用拒绝启动。
- 被禁用用户不能登录；已有 Token 在下一次请求时失效。
- 401 响应触发前端清理会话并跳转到 `/login`，不得依赖 hash 路由写法。
- 连续失败登录具备限速机制，并记录安全日志。

### FR-02 用户与角色管理（P0）

需求：管理员可分页查询、创建、编辑、启停用户，分配角色和重置密码。

验收：

- 用户名唯一且不可为空；密码满足可配置强度规则。
- 不允许管理员禁用或降权系统内最后一个有效管理员。
- 用户列表不返回密码哈希等敏感字段。
- 所有角色变更均记录变更前后值。

### FR-03 学生档案（P0）

需求：维护学号、姓名、性别、出生日期、联系方式、地址、班级、状态和备注。

验收：

- 学号全局唯一；创建后是否允许修改由系统配置决定，默认禁止。
- 状态仅允许“在读、休学、退学、毕业”，非法值返回字段级错误。
- 邮箱、手机号、出生日期格式合法；出生日期不得晚于当前日期。
- `class_id` 必须指向有效且未删除班级。
- 更新接口应允许显式清空可选字段，不能因忽略 `null` 而无法清空。
- 列表支持分页、排序、组合筛选，并在筛选变化后回到第一页。

### FR-04 班级管理（P0）

需求：维护班级名称、入学年份、班主任和状态，并查看实际学生数量。

验收：

- 同一入学年份内班级名称唯一。
- 有在册学生的班级不能直接删除；系统提供转移学生或停用班级的路径。
- 入学年份默认使用当前年份，不使用写死的 `2024`。
- 班级数量统计与未删除学生数据一致。

### FR-05 搜索与列表（P0）

需求：统一支持关键词、班级、性别、状态、创建时间等组合筛选及排序。

验收：

- 搜索条件可在 URL 中恢复，刷新或返回页面后不丢失。
- 无结果、加载中、请求失败三种状态有不同反馈。
- 5 万条学生数据下，常用组合查询 P95 不超过 1 秒。
- 服务端限制最大分页大小，避免一次性拉取全部数据。

### FR-06 Excel 导入（P0）

需求：提供版本化模板、预校验、确认导入、结果报告和错误文件。

验收：

- 限制文件类型、文件大小和最大行数，服务端不得只依赖扩展名判断。
- 每条错误包含 Excel 行号、字段、原值及错误原因。
- 日期单元格按日期类型正确解析，不把日期时间字符串直接写入 Date 字段。
- 班级可按稳定编码匹配；不存在时不得静默丢弃。
- 导入在事务或可恢复批次内执行，部分失败策略必须由用户在确认页知晓。
- 导入任务具备幂等标识，刷新页面或重复点击不会重复导入。

### FR-07 Excel 导出（P0）

需求：导出当前筛选结果，并可选择字段。

验收：

- 导出筛选条件与列表一致，包括性别、状态和后续新增条件。
- 导出受角色及数据范围控制，且记录操作人、条件和结果数量。
- 大数据量导出转为异步任务，不阻塞普通 API 请求。
- 文件名包含日期时间，中文文件名兼容常见浏览器。

### FR-08 批量操作（P1）

需求：支持批量删除、恢复、调班和状态变更。

验收：

- 服务端返回实际成功、失败和未找到数量，不以请求 ID 数量冒充删除数量。
- 批量操作必须校验每条记录权限，并提供失败明细。
- 操作前展示影响预览，操作后可通过任务记录追踪。

### FR-09 回收站（P0）

需求：学生和班级采用软删除，管理员可筛选、恢复和按策略永久清理。

验收：

- 普通列表、统计、导出默认排除已删除数据。
- 恢复时重新校验学号、班级等唯一性和关联约束。
- 默认保留期建议 30 天，最终值由产品确认。

### FR-10 审计日志（P0）

需求：记录登录、创建、更新、删除、恢复、导入、导出、账号和权限变更。

验收：

- 日志至少包含操作人、动作、对象类型、对象 ID、时间、结果、来源 IP、请求 ID。
- 数据更新记录字段级前后差异，并对密码、Token 等敏感信息脱敏。
- 审计日志不可由普通业务角色修改或删除。
- 管理员和审计员可按时间、用户、动作和对象查询。

### FR-11 仪表盘（P0）

需求：展示学生总数、状态分布、性别分布、班级数量、近 30 日新增和待处理导入任务。

验收：

- 指标口径在页面提供说明，且默认排除软删除数据。
- 用户只能看到其数据权限范围内的统计。
- 空数据时显示零状态而不是报错。

## 8. 数据模型要求

### 8.1 Student

保留现有字段，并新增：

- `deleted_at`、`deleted_by`：软删除信息。
- `version`：乐观锁版本，避免多人编辑覆盖。
- `created_by`、`updated_by`：数据责任人。
- 可选稳定组织字段：`department_id`、`major_id`（P1）。

约束：`student_no` 唯一；`status` 使用枚举或约束；常用筛选字段建立索引；时间统一保存为 UTC，展示时转换到配置时区。

### 8.2 Class

新增 `code`、`status`、`updated_at`、审计字段和软删除字段；`(grade, name)` 或 `code` 唯一。

### 8.3 User

新增 `must_change_password`、`last_login_at`、`failed_login_count`、`locked_until`、`updated_at`。生产环境不自动创建弱口令管理员。

### 8.4 AuditLog

建议字段：`id`、`request_id`、`actor_id`、`action`、`resource_type`、`resource_id`、`before_json`、`after_json`、`result`、`ip`、`user_agent`、`created_at`。

### 8.5 ImportJob / ExportJob

建议字段：任务类型、发起人、文件摘要、模板版本、状态、总数、成功数、失败数、结果文件、错误摘要、幂等键和起止时间。

## 9. 状态与生命周期

### 9.1 学生状态

`在读 → 休学 → 在读`；`在读/休学 → 退学`；`在读 → 毕业`。

- “退学”和“毕业”默认视为终态；逆向恢复需管理员权限并填写原因。
- 删除状态独立于学籍状态，不得用“退学”代替删除。

### 9.2 批量任务状态

`待校验 → 校验中 → 待确认 → 执行中 → 成功/部分成功/失败/已取消`。

- 进入“执行中”后，同一幂等键不得创建第二个执行任务。
- 系统重启后应能识别并恢复或明确终止未完成任务。

## 10. 接口规范

- API 统一以 `/api/v1` 为前缀，后续版本不得破坏现有客户端。
- 错误结构统一包含 `code`、`message`、`field_errors`、`request_id`。
- 分页结构统一包含 `items`、`page`、`page_size`、`total`。
- 列表支持白名单排序字段，禁止直接拼接任意排序列。
- 所有写接口应定义并发策略；批量和任务创建接口支持幂等键。
- OpenAPI 文档在开发/测试环境开放，生产环境按策略限制访问。
- 前端 API 地址通过环境变量配置，不固定为 `http://localhost:8000`。

## 11. 非功能需求

### 11.1 安全

- 密钥、初始管理员信息和 CORS 来源全部通过环境配置。
- 生产使用 HTTPS，密码采用可靠哈希，日志不记录密码和完整 Token。
- 上传文件校验 MIME、大小、行数和内容；防止公式注入和压缩炸弹。
- 对登录、导入、导出和批量操作限速。
- 定期依赖扫描并修复高危漏洞。

### 11.2 性能与容量

- 设计基线：5 万名学生、2 千个班级、200 个账号、50 个并发用户。
- 普通读取 P95 ≤ 1 秒，普通写入 P95 ≤ 2 秒。
- 单次同步导入上限建议 5,000 行；更大任务异步处理。
- 前端继续按路由拆包，并优化 Element Plus 体积警告。

### 11.3 可靠性与恢复

- 生产数据库建议 PostgreSQL；SQLite 仅用于本地开发或单机轻量部署。
- 每日自动备份，目标 RPO ≤ 24 小时、RTO ≤ 4 小时。
- 发布前执行迁移备份，迁移具备前滚或回滚说明。
- 关键批量操作不得因进程中断形成无法解释的半完成状态。

### 11.4 可观测性

- 结构化日志包含请求 ID、用户 ID、路由、状态码和耗时。
- 提供健康检查与就绪检查，覆盖应用和数据库连接。
- 监控 5xx、登录失败率、API 延迟、导入失败率和任务积压。

### 11.5 可用性与无障碍

- 桌面端适配 1366×768 及以上，核心查询可在平板完成。
- 所有表单错误紧邻字段展示；危险操作不只依赖颜色表达。
- 支持键盘操作、合理焦点顺序和可识别标签，目标达到 WCAG 2.1 AA 的核心要求。

### 11.6 兼容性

- 支持当前及前一个主版本的 Chrome、Edge。
- Excel 支持 `.xlsx`；`.xls` 只有在实际解析能力验证通过后才可对外承诺。当前后端使用 openpyxl，V2.0 默认不承诺旧版 `.xls`。

## 12. 前端体验要求

- 登录页不展示生产默认账号和密码。
- 无权限的入口和按钮不显示；直接访问路由时展示 403 页面。
- 统一加载、空状态、错误状态、确认和成功反馈。
- 表格筛选与 URL 同步，返回列表保持页码和滚动位置。
- 导入使用分步向导；批量任务提供进度、结果和错误下载。
- 导航新增仪表盘、用户管理、审计日志、回收站和任务中心，并按权限呈现。

## 13. 测试与发布验收

### 13.1 自动化测试

- 后端：认证、权限矩阵、学生/班级 CRUD、唯一性、软删除、导入校验和审计日志。
- 前端：路由守卫、权限显示、表单校验、筛选分页与错误状态。

- 数据迁移：从当前 SQLite 基线数据升级后记录数量及关键字段保持一致。

### 13.2 发布门禁

- 所有 P0 验收标准通过，P0/P1 缺陷清零。
- 前后端构建、测试、迁移演练、备份恢复演练通过。
- 生产配置不存在默认密钥、默认密码、调试模式和宽泛 CORS。
- 运维手册、回滚方案、初始化流程和用户操作说明齐备。

## 14. 交付路线

## 15. 已知风险

| 风险 | 影响 | 建议 |
|---|---|---|
| 默认账号密码与开发密钥 | 生产账号可被直接攻破 | P0 优先治理，生产缺失配置时拒绝启动 |
| 物理删除且无审计 | 数据不可恢复、责任不可追溯 | 引入软删除、回收站和审计日志 |
| 前端权限入口未完整控制 | 用户频繁遇到 403，误解系统权限 | 统一权限指令与路由元数据 |
| Excel `.xls` 承诺与解析库不一致 | 用户上传后运行时失败 | V2.0 只承诺 `.xlsx` 或增加真实 `.xls` 解析器 |
| 导入日期和班级映射不可靠 | 写入失败或数据悄然缺失 | 预校验、明确映射、错误报告 |
| SQLite 并发能力有限 | 多用户写入冲突 | 生产切换 PostgreSQL |
| 无自动化测试 | 变更易引入回归 | 先补核心 API 和 E2E 测试 |
| API 地址与 CORS 固定 | 非本机部署失败 | 环境变量化并提供部署模板 |

## 16. 待产品确认项

以下问题尚不能从现有代码确定，在进入详细设计前必须确认：

1. 实际部署范围是单个班级、单个学校，还是多校区/多租户？
2. 学号是全局唯一，还是仅在学校、入学年份或校区内唯一？
3. 教师/编辑员可查看全校数据，还是只能查看负责班级？
4. 查看员是否允许导出包含电话、地址等个人信息？
5. 删除数据保留期、审计日志保留期分别是多少？
6. 批量导入遇到部分错误时采用“全部回滚”还是“有效行提交”？
7. 是否允许导入覆盖已有学生；允许时哪些字段不可覆盖？
8. 是否需要对接统一身份认证、企业微信/钉钉或现有教务系统？
9. 学生个人信息适用的地区、组织安全规范和合规要求是什么？
10. V2.0 首次上线的预计学生数、并发用户数和可接受停机窗口是多少？

## 17. 实施就绪判断

当前结论：**可进入阶段 A 的技术设计与任务拆分，但不应直接开始全部 V2.0 功能开发。**

原因：工程和安全基线的约束已足够明确；数据范围、导出权限、导入覆盖策略和保留策略仍需产品负责人确认。上述待确认项中第 1、3、4、5、6、7 项会直接影响数据模型、权限模型和接口契约，应在阶段 B/C 开发前冻结。
